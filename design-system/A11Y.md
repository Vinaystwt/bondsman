# Bondsman Accessibility Rules

Scope: this file states the accessibility contract for every component built
in Tasks 11–24 (design-system/lab/components/*.tsx). It does not introduce
new components or new visual treatments — it names the rule each existing
component already follows (or must follow), so QA.md can check against it.

## 1. Contrast obligations

Every color pairing this system uses for text or a graphical UI element must
clear WCAG AA. This is not a manual judgment call — it is enforced by an
automated test:

- `design-system/TOKENS/test/contrast.test.mjs` (run via `node --test`)
  checks every required token exists and asserts two ratio classes:
  - **Text-on-surface (4.5:1):** `ink`/`surface`, `muted`/`surface`,
    `accent`/`surface`.
  - **UI-component/graphics (3:1):** `boundary`/`surface`,
    `destructive`/`surface`.
- Any new token or new text/background pairing must be added to this test
  before it ships. A component is never "probably fine" on contrast — if the
  pairing isn't in `contrast.test.mjs`, add it and run the test.
- `--consequential` is intentionally excluded from the text-contrast pairs:
  per PRINCIPLES.md Principle 3 it never carries body text, only the fill of
  a resolved-slash segment, so it is a fill-contrast concern handled visually
  (see PRINCIPLES.md), not a text-contrast one.

## 2. Keyboard focus rings

Every interactive element (button, link, control, tab stop) uses the exact
same focus-visible treatment — no component invents its own ring color,
width, or offset:

```
focus-visible:outline focus-visible:outline-2 focus-visible:outline-offset-2 focus-visible:outline-ink
```

This is `--ink`, not `--accent` — `--accent` is reserved and unused for
interactive chrome (see Button.tsx's header comment); a colored focus ring
would introduce a fourth chromatic meaning this system's token contract
doesn't allow. The pattern is already applied verbatim in Button.tsx,
CopyControl.tsx, Dialog.tsx, Drawer.tsx, MobileNavSheet.tsx, HashPill.tsx,
and EvidenceLabel.tsx. Any new interactive component must reuse this literal
string, not a variant of it (no `outline-4`, no `outline-offset-0`, no
`outline-accent`).

Focus is never suppressed: no `outline-none` without a replacement, no
`:focus { outline: 0 }`, on any focusable element, anywhere in the system.

## 3. `aria-live` announcement rules

State changes fall into two buckets:

**Announce (assertive or polite live region, per severity):**
- Lifecycle transitions (Initiated → Bonded → Executed → Challenged →
  ResolvedSlash/ResolvedRefund) — the user must hear that the bond's real
  status changed, since the visual crossfade (MOTION_SPEC.md §5) carries no
  information to a screen-reader user on its own.
- Payment ladder advances (one `PaymentState` position becoming the next) —
  same reasoning: a rung advancing is a real state change, not decoration.
- Wallet connection changes (connected → connecting → disconnected → error)
  — `WalletStateCard`'s state swap must be announced; a silent wallet
  disconnect is a trust failure, not just a visual one.
- Degraded/error banners (`Banner.tsx`) already carry this correctly today:
  `error`/`degraded` render with `role="alert"` (assertive), `info` renders
  with `role="status"` (polite) — see Banner.tsx's header comment. Any
  future live-region wiring for lifecycle/ladder/wallet state should follow
  the same severity split: routine advances get `role="status"`
  (`aria-live="polite"`), and only a genuine error/degraded condition
  escalates to `role="alert"` (`aria-live="assertive"`).

**Do not announce:**
- Hover state changes.
- Focus state changes (the focus ring itself is sufficient signal; the
  browser/AT already announces focus movement natively — a redundant live
  region on top of that is noise).
- Any purely decorative or ambient visual change (there are none in this
  system per MOTION_SPEC.md §1, but the rule is stated for completeness).

## 4. Reduced-motion behaviour

Every animation in this system has a named, static equivalent under
`prefers-reduced-motion` / `useReducedMotion()`. The full mapping — one line
per animation type (bond split, panel/card entrance, lifecycle/ladder
transitions, in-place number change, receipt sealing) — is specified in
`design-system/MOTION_SPEC.md` §9 ("Reduced-motion mapping"). That file is
the single source of truth for timing/easing and reduced-motion pairs; this
document does not duplicate the mapping, it points to it. Any new animated
component must add its reduced-motion equivalent to MOTION_SPEC.md §9 before
shipping.

Independent of user motion preference, Principle 5 ("motion stops at the
edge of trouble") means error/degraded/unavailable/disconnected states never
animate in at all — this is stronger than the reduced-motion preference and
applies unconditionally (see Banner.tsx, MOTION_SPEC.md §1 item 5).

## 5. Minimum target sizes

Every tap/click target is at least 44×44px, matching iOS/Android platform
guidance and WCAG 2.5.5 (AA-adjacent). `MobileNavSheet.tsx` is the reference
implementation: its close button and every nav row use
`min-h-[44px]`/`min-w-[44px]` explicitly (not just comfortable padding that
happens to reach 44px). Any new touch target — icon buttons, close controls,
row-level tap areas on mobile — must hit this floor explicitly with a
`min-h-[44px]`/`min-w-[44px]` class, not an assumption that padding alone
gets there.
